# Hoggy

Medical conference scanner: discover conferences, plan trips, forward receipts, claim expenses, track CPD.

## Run

```
npm install             # runtime dependencies: pdfjs-dist (reads PDF receipts), pg (Postgres, used only when DATABASE_URL is set),
                        # @anthropic-ai/sdk (reads receipt photos, used only when ANTHROPIC_API_KEY is set)
node server.js          # Node 22+; SQLite in data-store/ unless DATABASE_URL is set
```

Open http://127.0.0.1:8123. Without the server (any static host) the app still works in offline mode, with data on the device only.

## Backend (server.js)

- Accounts (scrypt, HttpOnly session cookie, rate-limited login/register; limits are stored in the database so every instance counts the same attempts), CSRF header check on every mutating call. Passwords need at least 10 characters (shown under the field).
- `GET/PUT /api/state` — per-user sync with revision conflict detection.
- Reviews belong to a conference **series** (every edition), keyed by `lib/series.js` (organiser tag + name with years, ordinals and edition numbers removed). One review per user per series per year attended (up to 10 years back), five ratings (content and speakers, networking, venue and organisation, value for money, CPD worth) and a comment of up to 600 characters.
  - `GET /api/reviews?series=<key>` (or `?conf=<id>`), `GET /api/ratings` (per series), `GET /api/my-reviews`; `POST /api/reviews` `{series, editions:[{year, city}], ratings, text}` adds one or more years at once; `PUT`/`DELETE /api/reviews/<id>` (author only); `POST /api/reviews/<id>/report`.
  - `POST /api/reviews/<id>/proof?kind=certificate|cpd|receipt` (PDF/JPG/PNG, 5 MB, magic bytes checked). Proof files are never served publicly: only `GET /api/admin/proofs/<id>/file` returns them, and they are deleted once an admin approves or rejects.
  - Share link `/#/review/<seriesKey>` opens the review form (sign-in first if needed).
  - `GET /api/top-rated?specialty=<name>&limit=<1-50>` — "Highest rated by attendees": series with 3+ reviews ordered by the weighted score (ties: more verified, more reviews, title). Built from the score cache; shown on Home under "How it works" (nothing until a series qualifies) and on Discover when sorting by it.
- "Covered in" (journal and press coverage, links only): `GET /api/coverage?series=<key>` (or `?conf=<id>`) returns approved links; `POST /api/coverage` `{series, type: meeting-report|abstract-supplement|society-journal|news, title, publication, year, url}` (signed in, https and a publication required) adds a pending suggestion. Admins approve, reject or add links at `/admin.html` (`/api/admin/coverage`).
- Emailed registration receipts that match an edition go to the admin desk (`GET /api/admin/receipts`, `POST /api/admin/receipts/<id>` approve|reject, `GET /api/admin/receipts/<id>/file` admin only; the admin copy of the file is deleted after the decision).
- `GET /api/courses` — course catalogue and upcoming sessions from `data/courses/catalogue.json` and `sessions.json` (bundled static files, like `data/conferences.js`; finished sessions are dropped; ETag). Without the server the app reads the same two files. Certificates ("My certificates") live in the synced state (`certs`), their files in the receipt file store (`c-` keys). Expiry comes from the catalogue's sourced validity (APLS 5 years, ALS 4 years), otherwise the user types it; reminders are in-app only (email needs D3). Check the data with `node tools/check-courses.js` (also run by `npm test`).
- **Hospitals (optional).** A doctor without a hospital uses Hoggy exactly as before. Settings, "Your hospital": set one up (you become its **admin** and get an 8-character join code, shown as `ABCD-EFGH`, no 0/O/1/I; you set the claims email, the yearly study allowance per doctor and the currency) or join with a code (you join as a **doctor**). One hospital per user. Roles: doctor, manager, finance, admin. Admins change roles, remove members, make a new code (the old one stops working) and edit the hospital; a hospital always keeps one admin (on account deletion the longest-standing manager, else member, takes over; the last member leaving removes the hospital).
  - **Trip approval:** on a trip, "Request approval" sends estimated registration, flights, accommodation and other costs (prefilled from the trip's last estimate, the study-leave draft or logged bookings). The request is a server record (`approvals`), never the synced state; the event details come from the server's own conference row (courses: the cleaned client description). Managers and admins decide on the **Approvals** page, with the doctor's budget for that year and what is left if approved; rejecting needs a comment; nobody decides their own request. A rejected request can be edited and resubmitted.
  - **Study budget** per person and year of the event's start date: allowance (hospital default, or a per-person, per-year figure a manager sets on the **Team** page), committed (approved, not yet claimed, at the estimate), spent (claims submitted or paid, at the claim-pack total), remaining; pending requests are shown, not subtracted. Shown on Home, on each trip and to approvers.
  - **Claims to finance:** "Email to claims admin" defaults to the hospital's claims email (a claims email typed in Settings, Your employer, still wins). "Mark submitted" creates a server claim with the pack total (it must be in the hospital's currency); **Finance claims** (finance and admins) lists them and "Mark paid" (not your own); the doctor then sees "Paid". Hoggy still sends no email: notices are in-app (Home, Settings) until decision D3.
  - Endpoints: `GET/POST /api/org`, `POST /api/org/join|leave|code|settings|allowance`, `GET /api/org/team?year=`, `POST /api/org/members/<userId>` `{role}|{action:'remove'}`, `GET /api/budget?year=`, `GET /api/approvals/mine`, `GET/POST /api/approvals`, `POST /api/approvals/<id>` `{action, comment}`, `GET /api/claims/mine`, `GET/POST /api/claims`, `POST /api/claims/<id>/paid`, `GET /api/notifications`, `POST /api/notifications/read` (`lib/hospital-api.js`, pure rules in `lib/hospital.js`).
  - Security: the hospital always comes from the caller's membership, never from the request; a record in another hospital is 404, a page your role cannot use is 403; doctors see only their own requests and claims; join attempts are limited to 10 per account and 30 per network per hour (`rate_hits`), and a wrong code gives no hint.
  - Navigation: Approvals, Team and Finance claims appear in the desktop sidebar only for the roles that use them. On phones the tab bar keeps its 7 tabs; these pages open from Settings, Your hospital, and Settings carries a badge for unread notices, requests to decide and claims to pay.
- **Snap receipt.** `POST /api/receipts/read` (signed in; raw file body with its `Content-Type`; JPG, PNG or WebP up to 5 MB, PDF up to 10 MB; the first bytes must match the type; HEIC is refused with a message, and the browser converts HEIC to JPEG where it can; 30 reads per user per hour in `rate_hits`, `HOGGY_READ_PER_HOUR`). Returns `{supplierName, supplierAbn, totalCents, gstCents, currency, date, isTaxInvoice, category, confidence, abnValid, source, note}`, every field validated on the server (`lib/receipt-reader.js`). PDFs with a text layer are read on the server by `parse.js`; photos and PDFs without text go to Claude only when `ANTHROPIC_API_KEY` is set (model `RECEIPT_MODEL`, default `claude-opus-5-5`, structured JSON output, low effort, server-side fallback on a refusal). Without the key, photos come back empty with low confidence. Nothing is stored by this call: the "Check this receipt" card shows the fields, all editable, and "Looks right" saves the receipt and its file the usual way. Offline or signed out, a snapped photo is still saved, just not read.
  - **Privacy:** receipt images (and PDFs without a text layer) are sent to Anthropic only when `ANTHROPIC_API_KEY` is set. Without it nothing leaves the server. Tell users before you set the key.
- **Receipt checklist per trip** (Trips and Claims): one line per category with an estimate above 0 (from the trip's approval request, its saved estimate, or the study-leave draft); without an estimate, Registration, Flights and Accommodation for a conference and Registration for a course. ✓ once a receipt of that category exists (Ground transport and Meals count as Other). "I don't have this receipt" needs a reason, kept in the synced state (`claims[tripId].waived`). Export, Email and Mark submitted stay available and show what is missing; the reasons go on the claim pack schedule (CSV "Schedule notes", printed pack, email body).
- **Tax-invoice check** (Australian-dollar receipts only, `pack.js taxFlags`): no supplier ABN, an ABN that fails the ATO check digits, GST shown without the words "tax invoice", and $82.50 or more including GST without an ABN. Each flag says the receipt "may not count as a tax invoice" and how to get one (for flights: the airline's Manage booking page). Flags never block; they are listed on the schedule.
- **Currencies:** `parse.js` reads ISO codes and symbols at the total (JPY, ¥, USD, US$, EUR, €, GBP, £, NZD, NZ$, SGD, S$ and more); a bare `$` is the home currency unless the document names a dollar currency or shows an ABN or GST (AUD). Claims show subtotals per currency; a foreign receipt without an exchange rate is marked "not in the total" and blocks export as before.
- `POST /api/inbound/email` with header `X-Hoggy-Secret` (or HTTP Basic, password = secret) — inbound-email webhook (Postmark-style JSON, or `{to,from,subject,text,attachments}`). Matches `dr-<token>@receipts.hoggy.app` to a user, parses the receipt, stores the attachment, and the app, while open, pulls it into Receipts within a minute.
- Storage goes through `lib/db.js`: **Postgres** when `DATABASE_URL` is set (production, see below), otherwise **SQLite** in `data-store/` (SQLite file, daily backups, inbound secret). Back that folder up; do not publish it.

### Organisers, public pages and the database being down (client-ready, Nov 2026)

- **List your event** (`#/list-event`, linked from the footer and Discover): a public form for conferences and course sessions, no account needed (signed-in users are linked). Fields: name, organiser, official event page (https), dates, city and country, canonical specialty, format, CPD only if the organiser's page states it, a contact email (kept privately in `submissions.contact_email`, never served publicly) and an "I'm authorised to list this event" tick. `POST /api/submissions`: 5 per network and 5 per contact email per hour (`rate_hits`), a hidden honeypot field (`website`: the request looks accepted and nothing is stored), the copy-lint word list on name, organiser and description. Rules in `lib/listings.js` (shared with the browser).
- **Admin desk, "Submitted events"** (`/admin.html`): the official page link, the private contact email, editable fields, Save edits, Approve and list, Reject. **Approve needs the admin's own paste of the date line from the official page** (`datesQuote`); the row is then checked against the evidence rule (`tools/evidence.js`: event page not a site root, on the organiser's domain, quote holds the start day) and the conference validator. Approved listings get `source: 'organiser-submitted'`, `datesSourceUrl` = the submitted page, `verifiedOn` = the approval date, an id starting `org-`, and CPD hours only when the admin ticks that the page states them.
- **Why approved listings survive the daily merge:** they are rows in the database's `conferences` table with source `organiser-submitted`, not lines in `data/conferences.js`. The seed only inserts new curated ids and updates rows whose source is `curated`, so `merge-shards.js` and a redeploy never touch them, and `/api/conferences` serves them with everything else. (Writing them to a shard was rejected: it needs a commit from the server, which Vercel cannot do, and the merge would re-validate and could drop them.) Trade-off: while the database is down they are missing from the bundled fallback list. Desks adding the same event later should check `organiser-submitted` rows to avoid a duplicate.
- **Report a problem with this listing** on every conference dialog, conference page and course page: wrong date, wrong city or venue, duplicate, not relevant, something else (+ note). `POST /api/reports` (public, 20 per network per hour, honeypot); admin queue "Listing problem reports" with Fixed / Dismiss (`/api/admin/reports`).
- **Server-rendered public pages** (`lib/pages.js`, no scripts, the app's stylesheet): `/about`, `/privacy`, `/terms` (both marked "Draft — review by a lawyer before launch"), `/conferences/<id>` and `/courses/<id>` (title, description, canonical link, Open Graph and Twitter card tags, schema.org Event JSON-LD for rows that are not estimates), a friendly 404 page for any unknown path, `/sitemap.xml` (every upcoming conference and every course), `/robots.txt` (allows the site, disallows `/api/` and `/admin`), `/manifest.webmanifest` and icons in `icons/` (drawn by `tools/make-icons.js`). The contact address on these pages is `HOGGY_CONTACT_EMAIL`, a placeholder until it is set.
- **Database down:** pages, the app shell, `/api/courses` and `/api/conferences` (from the bundled `data/conferences.js`, header `X-Hoggy-Fallback: bundled`) keep working; other `/api/*` calls answer JSON 503; the app shows "We're having trouble connecting — try again in a minute" with Try again, and sign-in explains it is unavailable. An organiser listing page that needs the database shows the friendly "trouble connecting" page (503). The app also shows an offline banner when the browser goes offline.
- Checks: `tests/client-ready.test.js` (in `npm test`); `NODE_PATH=/opt/node-tools/node_modules node tests/e2e/client-ready.js <dir>` (Playwright and axe-core at 390x844 and 1280x900, light and dark, keyboard-only flows, database down); `node tests/e2e/a11y.js` (axe on every route).

### Conference database and updater

The server keeps conferences in SQLite (seeded from `data/conferences.js`, new ids only) and serves them at `GET /api/conferences`; the app loads that list, falling back to the bundled file offline.

Start with `HOGGY_INGEST=1 HOGGY_ADMINS=you@example.com HOGGY_ADMIN_KEY=<long random string> node server.js` (the admin key is mandatory: without it all admin endpoints are disabled) to enable the updater (runs 30s after start, then every 6h):
- **Refresh:** re-checks each conference's organiser page (robots.txt respected, https only, private addresses blocked, polite delays). When the page publishes schema.org Event JSON-LD or iCal that matches a confirmed row's start date (the end-date check is still a no-op, B26), the row's `lastVerified` is re-stamped; any different date is queued in `date_changes` for an admin to approve (never applied on its own). The updater has not yet been run on the full dataset (D1). Dead links (3 strikes) and cancelled/postponed wording flag the conference with a warning in the app.
- **Discover:** polls `data/sources.json` (journal, society and publisher feeds: iCal, RSS, JSON-LD, Crossref) and queues unknown events as candidates. Nothing external goes live until an admin approves it at `/admin.html` (the Data desk).
- `node tools/merge-shards.js` merges curated JSON shards; `node tools/check-sources.js` writes an offline freshness report.
- **Date evidence (B30).** A conference shows "Dates confirmed" only when the row stores where and when Hoggy read the dates: `datesSourceUrl` (the organiser's or society's event page, https, not a site root or aggregator, on the organiser's domain or in `tools/official-domains.json`), `datesQuote` (the page's own words, at most 200 characters) and `verifiedOn`. Rows confirmed before this rule (17 Nov 2026) keep their dates with `legacyConfirmed: true` and show "Confirmed by organiser (source not yet re-checked)"; the home page and Discover count them separately. The merge step downgrades any other confirmed row without valid evidence to an estimate and records why in `estimateReason` (`tools/evidence.js` holds the rule).
- `node tools/validate-data.js` checks `data/conferences.js` and `data/shards/` (required fields, ISO dates, end after start, https, canonical specialty, ISO country codes and one spelling per country, unique ids and series-plus-start, the evidence rule, the copy-lint word list from `tools/copy-lint.js`) and prints the counts; it exits 1 on an error. It runs at the end of `npm test` and in CI, where CI also checks `data/conferences.js` is exactly what the merge produces.
- `node tools/verify-dates.js --limit 40` (daily, on the laptop) re-reads the 40 soonest estimated or legacy rows on the organiser's page and writes evidence to `data/shards/provenance-dates-<date>.json`, listing anything unclear under "Date checks" in `docs/daily-report-<date>.md`. Then `node tools/merge-shards.js && node tools/validate-data.js`. Details and the exact daily lines: `docs/team/country-desks.md`.

### Go live checklist

1. Host behind HTTPS with `HOST=0.0.0.0` behind a reverse proxy (cookies are `Secure` automatically unless HOST is loopback; set `HOGGY_TRUST_PROXY=1` so rate limits use the real client IP, and add HSTS at the proxy).
2. Point an MX record for your mail domain at an inbound-email provider (e.g. Postmark inbound) and have its webhook send `X-Hoggy-Secret: <HOGGY_INBOUND_SECRET>` (or Basic auth with that as the password) to `https://<host>/api/inbound/email`. Set `HOGGY_MAIL_DOMAIN` to that domain. Without `HOGGY_INBOUND_SECRET` the server makes one: SQLite keeps it in `data-store/inbound-secret.txt`, Postgres in `hoggy.meta` (key `inbound_secret`).

Known gaps: no email verification or password reset (needs outbound mail), so registration reveals whether an email exists and reviewers are not email-verified.
3. Receipt files are kept on the device (IndexedDB) and, when signed in, copied to the server's file store (`/api/rfile`); synced state covers trips, receipt metadata, CPD, certificates and settings.

## Deploying to Vercel

`vercel.json` sends every path to one Node 22 function (`api/index.js`, which reuses the handler from `server.js`). Locally nothing changes: `node server.js` still listens as before.

- Import the repo in Vercel; Framework Preset **Other**. Leave build, output and install settings at their defaults (`vercel.json` sets them; the empty `public/` output stops Vercel publishing the source tree as static files). Node.js version 22.x (from `package.json`).
- When `VERCEL` is set, the server marks cookies `Secure`, trusts `X-Forwarded-For`, never runs the updater (`HOGGY_INGEST` is ignored) and skips local backups. Functions run in Sydney (`"regions": ["syd1"]` in `vercel.json`), next to the Supabase database in ap-southeast-2: every request makes a few database round trips, so keep the two in the same region.
- **With `DATABASE_URL` set** (production) all data lives in Postgres and is shared by every instance. **Without it** the server falls back to SQLite in `/tmp/hoggy-data`, which is per instance and wiped when the instance is recycled (accounts vanish, sign-ins fail on another instance); the site then shows a small "Preview — accounts and receipts reset" notice. The notice disappears as soon as `DATABASE_URL` is set (it can be forced locally with `HOGGY_DEMO=1`).
- Request bodies on Vercel are limited to 4.5 MB, so proof uploads and receipt files above that size are refused by Vercel before they reach the app (the app's own caps are 5 MB and 16 MB).

## Production database (Supabase)

Postgres on Supabase (project `ipnkzavrbfzuphicycuc`, region ap-southeast-2). Everything lives in the schema `hoggy`; every table has row level security **on with no policies**, and `anon` / `authenticated` have no grants, so the public Data API (anon key) sees nothing. The server connects as `postgres`, which bypasses RLS.

1. **Schema.** Apply `db/postgres/001_init.sql`, then `db/postgres/002_receipt_checks_coverage.sql`, then `db/postgres/003_hospitals.sql` (hospitals, memberships, allowances, approvals, claims, notifications) in the Supabase SQL editor or with the Supabase tools. All are idempotent. The server runs every numbered file in `db/postgres/` in order on a cold start (it records each file's hash in `hoggy.meta`, `schema_hash` for 001 and `schema_hash:NNN` for later ones, and skips a file whose hash is unchanged; an advisory lock stops two instances running DDL at once), so applying them by hand first is optional but recommended.
2. **Vercel env vars** (Project, Settings, Environment Variables, Production; then redeploy):

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | Supabase, Connect, **Transaction pooler** URI (port **6543**): `postgresql://postgres.ipnkzavrbfzuphicycuc:<db-password>@aws-0-ap-southeast-2.pooler.supabase.com:6543/postgres` (copy the exact host from the dashboard) |
   | `HOGGY_INBOUND_SECRET` | a long random string (`openssl rand -hex 24`); the inbound-email provider sends it as `X-Hoggy-Secret` |
   | `HOGGY_ADMIN_KEY` | a long random string; admins send it as `X-Admin-Key` at `/admin.html` |
   | `HOGGY_ADMINS` | comma-separated admin emails, e.g. `you@example.com` |
   | `ANTHROPIC_API_KEY` (optional) | turns on reading receipt photos with Claude. Receipt images are then sent to Anthropic; without it nothing is sent |
   | `RECEIPT_MODEL` (optional) | the Claude model for receipts, default `claude-opus-5-5` |
   | `HOGGY_PG_CA` (optional) | Supabase's CA certificate (PEM text, Database Settings, SSL) to verify the server certificate; without it the connection is encrypted but the certificate is not checked |

3. Redeploy and open `/healthz`: it should say `"db":"pg"` and the conference count. The "Preview" notice is gone.

Notes:
- Transaction pooler: the server only uses unnamed statements (node-postgres `pg`, no prepared-statement names) and qualifies every table with the schema instead of relying on `search_path`, so PgBouncer/Supavisor transaction mode is fine. Tested through PgBouncer in transaction mode with `max_prepared_statements = 0`.
- Conferences are seeded from `data/conferences.js` only when the file changes (its hash is kept in `hoggy.meta`, key `conf_seed_hash`); admin edits are never overwritten.
- Sessions, rate limits (`hoggy.rate_hits`, hashed keys), the inbound secret (when the env var is missing) and files all live in the database, so any instance can serve any request. Scores (`/api/ratings`) are cached per instance for 15 s; the conference list is re-checked every 10 s.
- Receipt files and proof-of-attendance uploads are stored as `bytea` (16 MB and 5 MB caps; proofs are deleted once an admin decides). Supabase Storage (private bucket) is the better long-term home once volumes grow.
- Optional: `HOGGY_PG_SCHEMA` (default `hoggy`), `HOGGY_PG_POOL` (connections per instance, default 3).
- Backups: Supabase's daily backups cover the database; the SQLite backup job does not run with Postgres.

## Trust rules

- **Verified attendee** is decided on the server only, never from the request or from synced trip state, and always by an admin at `/admin.html`. Either (a) the server received, at the reviewer's private Hoggy address, a registration receipt that names the conference and is dated from 400 days before that edition to 7 days after it, and an admin approved that match (`verified_by='receipt'`), or (b) an admin approved an uploaded certificate of attendance, CPD certificate or registration receipt (`verified_by='admin'`). Otherwise a review shows "Attended (not verified)"; while a receipt or proof waits it is `pending_receipt` or `pending_proof` (still unverified).
- Scores are per series: a verified review counts in full, an unverified one counts half, and nothing is shown until a series has 3 reviews. Reports from accounts younger than 24h (`HOGGY_REPORT_MIN_AGE_H`) are ignored; 3 reports hide a review pending admin review. Organisers have no way to edit or delete reviews.
- Older per-conference reviews were moved into the series model on first start (old table kept as `reviews_v1`); every old "verified" flag was reset because it came from client state.
- Dates are shown as confirmed only when an organiser page was read (stored `sourceUrl` + `lastVerified`). CPD hours/accreditation are shown only when published; otherwise "check organiser".

## Not built

Live booking (needs airline/hotel partner APIs and keys; Hoggy opens prefilled searches), password reset and email verification (need outbound mail), receipt photo reading without an Anthropic key (PDFs with a text layer are read on the server; photos are read only when `ANTHROPIC_API_KEY` is set), accuracy measured on real receipts (B09), automatic currency rates (foreign receipts take a manually entered exchange rate).
